ZASTUPITELNOST · INCIDENTY · HRANICE PRAVOMOCÍ

Zástupce správce: jak udržet ekosystém v chodu.

Tento manuál je určen pro dlouhodobější nepřítomnost hlavního správce. Cílem není převzít vývoj ani bezpečnostní správu, ale bezpečně rozpoznat problém, provést běžný provozní zásah a včas eskalovat citlivé situace.

ROLE

Co může zástupce správce

  • otevřít Správu, diagnostiku a stav všech osmi aplikací,
  • kontrolovat registr, nasazené manifesty, ověření veřejných zdrojů a stav záložního snapshotu,
  • pracovat se Statistikami používání a souhrnnými anonymními reporty,
  • otevřít Evidenci přístupů, dohledat JTI a připravit zneplatnění,
  • použít Pohled kolegy a ověřit, co vidí běžný proškolený učitel,
  • na GitHubu zkontrolovat Actions, znovu spustit bezpečný workflow nebo nasadit předem připravenou opravu, pokud má přidělený omezený GitHub přístup.

POVÝŠENÍ STÁVAJÍCÍHO UČITELE

Když už je kolega proškolený učitel

  1. Ve Správě → Evidence přístupů otevřete jeho existující záznam.
  2. Klikněte na Vydat nový přístup; jméno, interní ID a dosavadní aplikace se předvyplní.
  3. Ve Vydavateli změňte roli na Zástupce správce. Dosavadní výběr aplikací zůstane zachován — role zástupce sama nepřidává nové aplikace ani školení.
  4. Nastavte platnost, načtěte svůj soukromý podpisový klíč a vydejte nový podepsaný soubor.
  5. Kolega nový soubor načte v Můj přístup. Teprve po ověření nového přístupu je vhodné starý učitelský JTI zneplatnit, aby nezůstaly dva paralelní platné přístupy.

Provozní přehled všech osmi aplikací zástupce vidí ve Správě i bez toho, aby mu byly automaticky odemčeny všechny aplikace k běžnému používání.

BEZPEČNOSTNÍ HRANICE

Co zástupce správce nedělá

  • nevydává správcovská oprávnění a nepovyšuje sebe ani jiné uživatele,
  • nemění podpisové klíče, veřejné důvěryhodné klíče ani bezpečnostní politiku,
  • nevkládá soukromé klíče do GitHubu, e-mailu nebo sdíleného disku,
  • nemění serverová tajemství, API klíče ani autentizační infrastrukturu,
  • neprovádí nevratné zásahy bez zálohy a bez jasného důvodu.

RYCHLÁ TRIÁŽ

Když kolega hlásí, že něco nefunguje

  1. Otevřete Pohled kolegy a ověřte problém ve stejném typu rozhraní.
  2. Ve Správě zkontrolujte stav registru, živých manifestů a konkrétní aplikace.
  3. Spusťte Diagnostiku. Pokud test ukáže konkrétní chybu, zaznamenejte její text a čas.
  4. Pokud je chyba v deployi, otevřete GitHub Actions příslušného repozitáře. Opakujte pouze známý bezpečný workflow; při nové chybě nejprve zachovejte log.
  5. Pokud je problém jen v oprávnění uživatele, otevřete Evidenci přístupů a ověřte platnost, JTI, roli a odemčené aplikace.

SCÉNÁŘ A

Studio hlásí fallback nebo neověřené manifesty

Kontrola zdrojů rozlišuje tři úrovně: přímo ověřený nasazený manifest, ověřený veřejný GitHub zdroj a samotný záložní snapshot. Snapshot tedy neznamená automaticky výpadek aplikace, ale znamená, že zdroj nebyl při poslední synchronizaci potvrzen.

  1. Zkontrolujte počet přímo ověřených nasazení, ověřených GitHub zdrojů a položek pouze na snapshotu.
  2. Spusťte diagnostiku.
  3. V GitHub Actions zkontrolujte poslední sync/build. Je-li to známá dočasná síťová chyba, lze workflow bezpečně opakovat.
  4. Pokud se chyba opakuje nebo manifest změnil strukturu, dále nezasahujte do bezpečnostní konfigurace a eskalujte.

SCÉNÁŘ B

Přístup učitele nefunguje

  1. Na Můj přístup zjistěte přesný důvod: expirace, chybějící aplikace, staré školení, revokace.
  2. V Evidenci přístupů dohledáte uživatele a JTI.
  3. Podezřelý nebo ztracený přístup lze označit k revokaci a exportovat aktualizovaný revokační soubor pro nasazení.
  4. Nový podepsaný přístup vydává plný správce. Zástupce bez plného správcovského oprávnění nepoužívá hlavní podpisový klíč.

SCÉNÁŘ C

GitHub Actions selhaly

  1. Nejdříve zjistěte, který job a který krok selhal.
  2. Nepřepisujte kód naslepo jen proto, aby kontrola zezelenala.
  3. Je-li chyba síťová nebo jednorázová, opakujte pouze selhaný job/workflow.
  4. Je-li chyba po novém commitu, porovnejte jej s posledním známým funkčním releasem. Rollback je bezpečnější než improvizovaná změna, pokud není příčina jednoznačná.
  5. Log a SHA commitu uchovejte pro hlavního správce.

DOČASNÝ PLNÝ SPRÁVCE

Když omezená role nestačí

Hlavní správce může vystavit samostatné plné oprávnění s krátkou expirací, typicky 7, 14 nebo 30 dní. Jde o mimořádný režim. Po expiraci se práva automaticky ztratí a běžné oprávnění zástupce zůstává oddělené.

Plné povýšení použijte jen tehdy, když je nezbytný zásah, který role Zástupce správce záměrně blokuje.

GITHUB

Doporučený externí přístup

Běžná role Zástupce správce GitHub vůbec nepotřebuje. GitHub přístup přidělte jen tehdy, pokud má kolega současně technicky zastupovat vývoj nebo deploy. V takovém případě používá vlastní GitHub účet a pouze nejnižší potřebná práva k vybraným repozitářům. Nikdy nesdílí účet, heslo, token, SSH klíč ani 2FA hlavního správce a jen kvůli provozní roli ve Studiu nedostává vlastnictví organizace.

ESKALACE

Kdy přestat zasahovat

Okamžitě eskalujte při podezření na kompromitaci podpisového klíče, úniku osobních údajů, problému se serverovými tajemstvími, nejasné revokaci správce, změně autentizace nebo situaci, kdy by oprava vyžadovala vypnout bezpečnostní kontrolu.
